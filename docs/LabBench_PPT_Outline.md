## 第二部分：框架架构详解 (6页，约7分钟)

### 第4页：框架总览 - 九节点Pipeline
**架构图**（占页面主要位置）:

```
[用户指令] → Analyzer → Normalizer → Asset Manager
                                      ↓
                              ┌───────┴───────┐
                              ↓               ↓
                       Skill Planner  ‖  Condition Planner
                              ↓               ↓
                              └───────┬───────┘
                                      ↓
                         Code Generator → Registration
                                      ↓
                            Simulation → Reviewer
```

**设计原则**:
- **神经符号分离**: 神经组件（Analyzer/Planners）负责理解，符号组件保证物理准确性
- **模块化**: 9个独立节点，职责清晰
- **可复现性**: 确定性代码生成

**预留插图框**: [架构图详细版本] - 完整pipeline流程图

### 第5页：核心创新I - 神经符号AST解析
**Analyzer节点功能**:

**输入**: 自然语言实验指令
**输出**: 实体绑定的神经符号AST

**关键设计**:
- **实体提取**: 识别物理对象并赋予语义属性
- **步骤接地**: 将指令分解为实体引用的原子步骤
- **AST结构**: 保持层级和时序依赖

**示例对比**:

```
原文: "Pick up the beaker from water bath and pour into test tube"

❌ 传统方法: 模糊的语义表示，难以映射到物理执行

✅ 神经符号AST:
  实体: <beaker_0>, <test_tube_0>, <water_bath>
  步骤: pick(beaker_0) → lift → pour(beaker_0, test_tube_0)
```

**创新点**: 严格解耦语义理解与动作执行，为下游规划提供结构化中间表示

---

### 第6页：核心创新II - 并行双规划器架构
**Fan-in架构设计**:

**Skill Planner（技能规划器）**
- **状态驱动CoT**: 预/后状态断言追踪长程依赖
- **零硬编码规则**: 完全LLM驱动决策
- **技能库**: 20+原语（pick/place/lift/pour/stir等）

**Condition Planner（条件规划器）**
- **逐步物理验证**: 每步生成可验证成功条件
- **并行执行**: 与Skill Planner同时运行，互不依赖
- **条件类型**: is_grasped/lift/on/contain/pour_into等

**协同机制**:
```
           相同输入
              ↓
    ┌─────────┴─────────┐
    ↓                   ↓
Skill Planner    Condition Planner
    ↓                   ↓
    └─────────┬─────────┘
              ↓
       Code Generator (汇聚点)
```

**创新点**: 首次将技能规划与验证条件生成解耦并行，提升效率的同时保证严谨性

**预留插图框**: [Fan-in架构对比图] - 对比串行vs并行的效率差异

### 第7页：核心创新III - 动态人为干预建模
**现实痛点**: 真实实验室中，人为干预无处不在（同事调阀门、温度变化、设备重定位）

**传统仿真的缺失**: 大多数基准假设静态环境，无法评估agent的鲁棒性

**LabBench解决方案**: 程序化环境扰动机制

**四大干预类型**:
1. **仪器状态切换**: 阀门开闭、加热器启停
2. **试剂添加**: 中途引入新物质
3. **设备重配置**: 支撑结构重新定位
4. **外部扰动**: 施加力或干扰

**实现机制**: 通过Simulation节点修改实体状态、添加物质、施力

**评测价值**: 评估agent的检测、适应、规划调整能力

### 第14页：主实验结果 - 性能对比
**核心发现**（突出对比）:

**传统二元评估**:
- ACT: ~60% 成功率

**严格物理验证后**:
- ACT: ~25% 成功率 ⬇
- Diffusion Policy: ~30% 成功率 ⬇
- π₀: ~35% 成功率 ⬇

**关键洞察**: 
- 二元指标严重高估模型性能
- 性能下降幅度达 **40-50%**
- 揭示SOTA模型在物理验证下的真实能力

### 第15页：逐步物理验证的威力
**案例分析**: pick_tube_pour_object任务

**二元评估视角**:
```
✅ 所有技能执行完成 → 任务成功 (100% success rate)
```

**逐步物理验证视角**:
```
Step 1 (pick):     ✓ 试管被成功抓取
Step 2 (lift):     ✗ 高度未达阈值 (8cm < 15cm)
Step 3 (pour):     ✗ 液体质量转移不足 (0.3g < 1g)
Step 4 (place):    ✓ 试管放置到目标位置
─────────────────────────────────
真实结果: ✗ 任务失败 (物理状态未达标)
```

**核心洞察**: 
- 机械臂"看起来"完成了动作，但物理状态未达标
- 揭示补偿性错误（最后一步成功掩盖前面的失败）
- 传统指标无法捕捉这类问题

**预留插图框（小）**: 
- **[示意图: 二元vs逐步验证对比]**
  - 内容描述: 可视化展示两种评估方法的差异

### 第16页：动态干扰场景影响分析
**实验对比**:

**静态环境 vs 动态干扰**:
- 静态环境: SOTA模型平均成功率 **65%**
- 动态干扰: 成功率骤降至 **30-35%**

**主要失败模式**:
1. ❌ **未检测变化**: agent忽略环境状态改变
2. ❌ **计划僵化**: 无法适应新条件调整动作
3. ❌ **状态丢失**: 长程任务中状态跟踪失败

**启示**: 
- 现有模型在动态环境下鲁棒性严重不足
- 真实实验室环境充满不确定性，这是关键能力缺口

**布局**: 对比柱状图 + 失败模式分类
