# Paper-to-Benchmark 纳入标准与第一版任务筛选（v1）

## 1. 文档目标

本文档用于规范 **Paper-to-Benchmark** 路线下的论文筛选与任务纳入流程。核心目标不是“从任意科研论文自动复刻实验”，而是：

> 从**适合编译**的机器人/实验自动化论文中，自动抽取结构化任务描述，并编译为 **MuJoCo 中可执行、可验证的 embodied benchmark task**。

这里的重点是 **compilation**，而不是单纯 scene generation。也就是说，纳入的论文必须能够支持以下信息的稳定抽取与形式化表示：

- 任务目标
- 实体与仪器
- 关键步骤
- 前置条件
- 终止条件
- 评测指标
- 失败模式

---

## 2. 总体原则

### 2.1 研究问题限定

我们不追求：

- 从任意论文中端到端自动生成完整实验复现
- 高保真复刻复杂流体、反应动力学或专用仪器物理行为
- 完全等价于真实论文中的全部实验条件

我们追求的是：

- 从论文中提取**任务等价（task-equivalent）**的结构化表示
- 在 MuJoCo 中构建**交互等价（interaction-equivalent）**的仿真任务
- 自动生成**评测等价（evaluation-equivalent）**的 success condition、protocol constraints 和 failure annotations

因此，MuJoCo 中的 benchmark 场景不要求“物理细节全还原”，但要求在以下方面与原论文任务保持一致：

1. **实体角色一致**
2. **关键交互一致**
3. **规程约束一致**
4. **成功判据一致**

---

## 3. 纳入标准（Inclusion Criteria）

只有当论文中的任务满足以下条件时，才可纳入 benchmark 候选池。

### 3.1 任务目标明确

论文必须清楚描述机器人需要完成什么具体任务，而不仅仅是抽象研究目标。

**适合纳入的例子：**
- 抓取并转运样品瓶
- 将样品瓶插入指定 rack
- 为试管封盖或开盖
- 使用手动移液器完成分液
- 将试管整理到目标试管架
- 执行实验器皿的台面转运

**不适合纳入的例子：**
- “提升实验自动化效率”
- “支持实验室自主科研”
- “提高化学实验吞吐量”

这些表述过于抽象，无法直接转化为 success condition。

---

### 3.2 实体与工具可枚举

论文中涉及的对象、工具、容器、仪器必须是有限且可列举的。

**优先纳入：**
- vial
- rack
- tray
- pipette
- pipette tip
- beaker
- tube
- holder
- cap
- valve / knob / switch

**谨慎纳入：**
- 依赖大量隐含设备配置
- 关键工具在正文中未明确说明
- 多种对象角色混乱、缺少图示支撑

---

### 3.3 关键步骤可分解

任务必须能够拆分为 **3–10 个事件级关键步骤**，并形成可执行 protocol graph。

**适合的任务结构：**
- 抓取 → 对齐 → 插入
- 识别 → 取枪头 → 吸液 → 移动 → 分液
- 抓取 → 旋转 → 松开
- 取出 → 移动 → 排列 → 放置

**不适合的任务结构：**
- 主要依赖一个连续黑盒 skill
- 关键过程无法从论文中拆成离散事件
- 只有高层目标，没有中间可解释步骤

---

### 3.4 前置条件与顺序约束清楚

论文中应存在足够信息，使任务能够形式化为带约束的 protocol。

**可接受的约束类型包括：**
- 必须先抓取后插入
- 必须先附着枪头再吸液
- 必须先开盖再转移
- 必须在对齐完成后再插接
- 必须按指定顺序整理对象

如果论文中完全无法恢复前置条件、步骤依赖和顺序关系，则不适合纳入。

---

### 3.5 终止条件可自动判定

任务必须存在可写成环境状态判断的终态。

**示例：**
- 样品瓶位于目标 rack 的指定槽位
- cap 被成功旋紧到阈值角度
- 枪头已附着且液体成功分配到目标容器
- 所有试管已被整理到对应 rack 位置
- 阀门已旋到目标角度区间

若只能依赖人工主观判断，则不适合作为第一版 benchmark。

---

### 3.6 失败模式可系统化标注

任务应当支持 failure mode taxonomy，而不是仅有 success/fail。

**优先保留支持以下失败模式的任务：**
- 抓取失败
- 错误对齐
- 插入失败
- 漏步骤
- 顺序错误
- 容差超标
- 使用错误对象
- 未满足前置条件即继续执行

---

### 3.7 MuJoCo 可复现性充足

任务的关键交互应主要依赖以下能力：

- 刚体操作
- 接触动力学
- 抓取与放置
- 对齐与插接
- 简单旋转/开合
- 参数化转移
- 有限状态更新

**不建议第一版纳入：**
- 强依赖高保真流体
- 强依赖化学反应动力学
- 强依赖柔性材料连续形变
- 强依赖显微、光谱、复杂力觉反馈
- 强依赖专用高端传感器闭环

MuJoCo 的强项在于快速、准确、可控的接触丰富动力学仿真，而不是实验室复杂多物理平台。

---

### 3.8 资产可获得性足够高

论文涉及的关键对象应满足以下至少一种条件：

1. Objaverse 或类似资源中可找到可替代资产
2. 现有 MuJoCo / MJCF 资产中已有近似对象
3. 可低成本手工建模为简化版本
4. 可通过功能等价替代物体表达

如果任务依赖大量难以获得的专用仪器几何、内部机构或复杂夹具，则不适合作为第一版 benchmark。

Objaverse 提供大规模 3D 物体资产，但其资产更适合作为候选对象库，而非默认可直接仿真使用的实验资产库。

---

## 4. 排除标准（Exclusion Criteria）

以下论文或任务原则上不纳入 v1 benchmark：

### 4.1 高保真流体主导任务
例如：
- 液滴形态决定任务成败
- 混合/扩散/流变行为本身是核心研究对象
- 必须依赖液面连续视觉反馈

### 4.2 化学反应动力学主导任务
例如：
- 任务成功依赖反应进程本身
- 反应机理、生成物状态、动力学参数是评价核心

### 4.3 复杂柔性体/材料形变主导任务
例如：
- 软管整理
- 薄膜操作
- 凝胶/胶体处理
- 布料/电缆/软组织实验操作

### 4.4 专用传感器主导任务
例如：
- 光谱仪读数闭环控制
- 显微成像驱动操作
- 高精度力控闭环
- 依赖复杂多模态实验传感

### 4.5 论文描述严重不完整
例如：
- 关键对象不明确
- 关键步骤无法恢复
- 成功判据模糊
- 图文均不足以重建任务结构

---

## 5. 论文筛选评分表（Paper-to-Benchmark Suitability Score）

每篇候选论文按以下 8 项打分，每项 0–2 分。

### 评分项

#### 1. 任务目标是否明确
- 0：模糊，无法写成任务目标
- 1：基本明确
- 2：可直接写成 success condition

#### 2. 实体/工具是否可枚举
- 0：大量隐含
- 1：大部分明确
- 2：基本都可列举

#### 3. 关键步骤是否可拆解
- 0：连续黑盒 skill
- 1：可粗略拆解
- 2：可稳定拆为事件序列

#### 4. 前置条件/顺序约束是否清楚
- 0：几乎没有
- 1：部分可恢复
- 2：可形成 protocol graph

#### 5. 终止条件是否明确
- 0：难定义
- 1：能人工判断
- 2：能自动判定

#### 6. 失败模式是否可标注
- 0：只有成功/失败
- 1：少量可解释失败
- 2：可形成系统 failure taxonomy

#### 7. MuJoCo 可复现性
- 0：明显依赖复杂多物理
- 1：可强近似
- 2：主要是刚体/接触/参数操作

#### 8. 资产可获得性
- 0：关键资产基本拿不到
- 1：可部分替代
- 2：关键资产大多可获得或易建模

### 评分解释
- **13–16 分**：优先纳入第一版 benchmark
- **9–12 分**：可纳入候选池，需人工补标/替代资产
- **0–8 分**：不建议纳入 v1

---

## 6. 资产策略（Objaverse / 自建 / 替代）

### 6.1 A 类任务：直接可用资产
对象在 Objaverse、现有 MuJoCo 资产或常见 CAD 库中容易获得，稍作清洗即可用。

**示例：**
- vial
- rack
- tray
- bottle
- cap
- beaker
- tube
- switch
- knob

### 6.2 B 类任务：功能等价替代
论文中的具体对象可由功能相近物体替代，不影响任务核心结构。

**示例：**
- 某型号样品架 → 标准 rack
- 某型号旋钮 → 通用 rotary knob
- 某品牌样品盒 → 标准分槽容器

### 6.3 C 类任务：需自建简化资产
任务关键对象无法可靠获得，必须手工建模简化版本。

**示例：**
- 专用实验夹具
- 特定插接接口
- 复杂仪器手柄
- 专用支架

**v1 建议：**
- 以 A+B 类任务为主
- 少量 C 类任务可作为展示
- 避免大规模资产重建拖慢 benchmark 开发

---

## 7. 第一版任务选择原则

v1 benchmark 不追求覆盖全部实验室任务，而是优先纳入：

1. **目标明确**
2. **步骤清楚**
3. **终态易判定**
4. **MuJoCo 友好**
5. **资产可得**
6. **failure mode 丰富**

优先做出一组 **小而硬** 的 benchmark 任务模板，再考虑扩展。

---

## 8. 第一版建议任务（v1 task pool）

以下任务适合作为第一版 benchmark 起点。

---

### Task 1: 手动移液器取枪头与定点分液
**论文来源：**  
*Integrating a Manual Pipette into a Collaborative Robot Manipulator for Flexible Liquid Dispensing*。论文描述了协作机械臂操作手动移液器、检测 labware 位姿、附着一次性枪头并进行精确液体分配。

**适合原因：**
- 目标明确：完成枪头附着与定点分液
- 步骤清楚：对位、取枪头、吸液、移动、分液
- 可用 protocol graph 表达
- 可用体积 bookkeeping 近似液体状态
- MuJoCo 中不必高保真模拟连续流体

**主要 evaluator：**
- 枪头是否成功附着
- 是否到达目标容器
- 分液位置是否正确
- 分液体积是否在容差内
- 是否按正确步骤执行

**难点：**
- 需要为体积状态设计抽象变量
- 需要明确液体转移的离散/参数化表示

---

### Task 2: 样品瓶封盖（Vial Capping）
**论文来源：**  
*Multimodal Behaviour Trees for Robotic Laboratory Task Automation*。论文直接包含 sample vial capping 任务，并强调实验室任务执行验证。

**适合原因：**
- 任务目标非常明确
- 刚体接触 + 旋转交互，适合 MuJoCo
- 终态可自动判定（角度/锁紧阈值）
- failure mode 清晰（未对齐、未旋紧、掉落）

**主要 evaluator：**
- cap 是否抓取成功
- cap 是否对齐到瓶口
- 是否旋到目标角度/紧固阈值
- 是否发生顺序错误或掉落

---

### Task 3: 样品瓶开盖（Vial Decapping）
**论文来源：**  
与 Task 2 同源，可构成对偶任务。

**适合原因：**
- 与封盖共享资产
- 可用于测试旋转方向、预抓取姿态和开盖规程
- 适合作为 protocol-sensitive benchmark task

**主要 evaluator：**
- 是否先抓稳瓶体/盖体
- 是否沿正确方向旋转
- cap 是否成功脱离
- 是否造成瓶体偏移/掉落

---

### Task 4: 实验架插入（Laboratory Rack Insertion）
**论文来源：**  
*Multimodal Behaviour Trees for Robotic Laboratory Task Automation* 中包含 laboratory rack insertion。

**适合原因：**
- 目标与终态清晰
- 关键交互是典型 pick-align-insert
- failure mode 丰富
- 很适合作为 benchmark 中的几何对齐任务模板

**主要 evaluator：**
- 是否抓取 rack 成功
- 是否完成对齐
- 插入深度是否达标
- 是否发生卡住、碰撞、误插

---

### Task 5: 样品瓶从源架抓取并插入目标架
**论文来源：**  
*Leveraging Multi-modal Sensing for Robotic Insertion Tasks in R&D Laboratories*。摘要明确描述了从 rack 中拿起 vial 并插入目标 rack 的任务。

**适合原因：**
- 多阶段但结构清晰
- 终态易判定
- 资产需求可控
- 很适合构造 protocol correctness 与 alignment benchmark

**主要 evaluator：**
- vial 是否从源 rack 正确取出
- 是否移动到目标 rack
- 是否正确插入指定槽位
- 是否有顺序错误或掉落

---

### Task 6: 试管分类与试管架整理
**论文来源：**  
*Arranging Test Tubes in Racks Using Combined Task and Motion Planning*。论文关注将混放试管识别、规划并整理到 rack。

**适合原因：**
- 多对象操作
- 长程任务结构明显
- 最终配置易自动判定
- 可自然引入排序/布局约束

**主要 evaluator：**
- 是否全部试管被移动
- 是否按目标布局归位
- 是否有放错位置
- 是否出现掉落或漏放

---

### Task 7: 实验器皿 / Labware 转运
**论文来源：**  
与 LAPP / labware transfer 方向相关的实验室自动化工作，重点围绕实验器皿转运。

**适合原因：**
- 简洁、通用、低门槛
- 适合做 v1 benchmark 的基础任务
- 资产获取容易
- 可作为更复杂任务的前置模板

**主要 evaluator：**
- 是否抓取正确对象
- 是否移动到目标位置
- 是否满足放置姿态要求
- 是否避免碰撞和掉落

---

## 9. 暂不纳入 v1 的代表性任务

### 9.1 粉末/刮取/材料处理类任务
例如 vial scraping、粉末刮取、颗粒处理等。  
这类任务虽然有研究价值，但更依赖材料特性、接触力和复杂行为，不适合作为第一版 compiler 的入口。相关工作已构建特定 scraping 仿真环境，但不宜作为 v1 的主要 benchmark 模板。

### 9.2 96 孔板自动液体处理全流程
例如枪头更换、吸液、分液、孔板定位、设备协作等复杂流程。  
这类任务很强，但系统复杂度高，更适合在 v2/v3 中纳入。

### 9.3 高保真化学实验还原
例如依赖复杂反应进程、流体动力学和连续液面行为的任务。  
不适合在当前 MuJoCo + Objaverse + task compiler 路线下作为第一版任务。

---

## 10. 第一版论文筛选流程（建议）

### Step 1：人工建立候选论文池
先整理 30–50 篇候选论文，不做自动海量抓取。

### Step 2：按评分表打分
对每篇论文从以下维度评分：
- 任务明确性
- 实体可枚举性
- 步骤可拆解性
- 约束清晰度
- 终态可判定性
- failure mode 丰富度
- MuJoCo 复现性
- 资产可得性

### Step 3：只保留高分论文
优先保留总分 **13 分以上** 的论文进入 v1 task pool。

### Step 4：人工补全 gold task spec
对高分论文人工建立 gold annotation：
- 任务目标
- 实体列表
- 关键事件
- 前置依赖
- 终止条件
- evaluator hooks
- failure tags

### Step 5：再评估自动编译器
让 LLM / LangGraph 系统自动从论文中抽取同样的信息，并与 gold spec 对比。

---

## 11. 当前建议的 v1 任务组合

建议 v1 以以下 6 类任务为主：

1. 手动移液器取枪头与定点分液
2. 样品瓶封盖
3. 样品瓶开盖
4. 实验架插入
5. 样品瓶从源架抓取并插入目标架
6. 试管分类与试管架整理

可选补充：
7. 实验器皿 / labware 转运

这组任务的共同特点是：

- 都来自真实论文场景
- 都可拆成结构化 protocol
- 都支持终态自动判定
- 都能在 MuJoCo 中以较低成本实现
- 大部分资产可通过 Objaverse / 替代资产 / 自建简化资产获得
- 都适合作为 paper-to-benchmark compiler 的第一版验证对象

---

## 12. 一句话定义

> 一篇论文中的任务，只有当它能被提炼为  
> **(1) 有限实体集合，(2) 有限关键事件集合，(3) 明确前置与顺序约束，(4) 自动可判定终止条件，(5) 在 MuJoCo 中可表达的关键交互**  
> 时，才纳入 benchmark。

---

## 13. 后续工作建议

### 13.1 先做 2 个模板任务
优先建议：
- 样品瓶封盖 / 开盖
- 实验架插入

因为这两类任务：
- 结构清楚
- evaluator 容易设计
- MuJoCo 实现成本低
- 很适合验证 compiler pipeline

### 13.2 建立 gold task spec 模板
每个任务至少包括：
- instruction
- entity list
- protocol graph
- hard constraints
- soft constraints
- goal state
- evaluator hooks
- failure modes

### 13.3 从“自动抽取正确率”开始验证
不要一开始就追求端到端自动生成。  
先验证：
- 任务目标抽取正确率
- 实体抽取正确率
- 关键步骤抽取正确率
- 协议图恢复正确率
- evaluator 生成可执行率

---

## 14. 结论

Paper-to-Benchmark 方向是可行的，但其可行性依赖于**严格的论文纳入标准**。  
v1 benchmark 应只覆盖那些：

- 任务明确
- 协议可恢复
- 终态可判定
- MuJoCo 可表达
- 资产可获得

的论文任务。

第一版不应追求“大而全”，而应优先选择 **小而硬、可编译、可验证、可解释** 的真实论文任务，建立方法学可信度，再逐步扩展到更复杂的实验室任务。
