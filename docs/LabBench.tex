\begin{abstract}
Scientific embodied agents have demonstrated tremendous potential in accelerating modern scientific discovery. Building physics-aligned embodied simulation platforms and benchmarks for scientific scenarios is foundational for low-cost agent training and rigorous evaluation. However, existing lab-oriented simulation platforms predominantly rely on experts manually orchestrating environments based on idealized assumptions. This heuristic design not only restricts the scale and scalability of evaluation tasks but also lacks effective modeling of dynamic human interventions, resulting in a substantial gap compared to real-world laboratory conditions. 

To address these limitations, we propose LabBench, a data-driven Real-to-Sim task compilation framework and scientific benchmark. This framework translates real-world experimental protocols into simulation code. First, a parser converts raw instructions into entity-bound neuro-symbolic Abstract Syntax Trees (ASTs), strictly decoupling semantics from actions. Scenes are then automatically constructed via asset retrieval. The core compilation framework utilizes a parallel Dual-Planner. While employing a state-based Chain-of-Thought (CoT) to orchestrate continuous actions, it concurrently deploys a condition planner to dispatch low-level verification criteria. Specifically, to introduce the complexity of human interventions into the simulation, the framework approximates human-robot interaction by injecting programmatic environmental alterations (e.g., instrument state toggles, reagent additions) into the experimental equipment. This automated pipeline significantly simplifies task creation and enhances benchmark scalability. 

Leveraging this pipeline, we distill protocols from frontier literature to construct a benchmark containing over 100 core test tasks (including 20+ dynamic interference scenarios), covering over 20 typical robotic manipulations and 100+ experimental instruments. Backed by the underlying physics engine, the dataset derives a massive number of evaluation episodes featuring topological changes and rigid-body physical noise. Preliminary evaluations on mainstream policy models (ACT, Diffusion Policy, $\pi_0$) demonstrate the significant challenge posed by LabBench. Step-by-step physical state verification exposes the overestimation issues inherent in traditional binary evaluation metrics. Current evaluation trends indicate a precipitous drop in the success rates of state-of-the-art models upon the introduction of rigorous physical and state validation, highlighting the severe compounding error bottleneck in long-horizon tasks. The pipeline code, benchmark dataset, and expert demonstration trajectories have been open-sourced.\end{abstract}

\section{Introduction}

Scientific embodied agents have emerged as a promising paradigm for accelerating modern scientific discovery \cite{drori2023ai, segler2018planning}. By integrating advanced reasoning capabilities with physical interaction, these agents can autonomously design and conduct experiments, analyze results, and iterate on hypotheses---fundamentally transforming how scientific research is performed \cite{king2009automating, scanlon2017scientific}. However, developing capable scientific agents requires substantial amounts of training data and rigorous evaluation methodologies, both of which depend on high-fidelity simulation platforms that accurately capture the complexity of real-world laboratory environments.

Building physics-aligned embodied simulation platforms for scientific scenarios presents unique challenges compared to general robotics simulation \cite{zhu2023mujoco, teng2021isaac}. Laboratory environments involve complex manipulations of specialized instruments, precise chemical and physical interactions, and often require multi-step reasoning under uncertainty. Existing lab-oriented simulation platforms predominantly rely on domain experts to manually orchestrate environments and tasks based on idealized assumptions \cite{bohg2023perspective}. This heuristic design approach suffers from several critical limitations: (1) it restricts the scale and scalability of evaluation tasks due to the high cost of manual creation; (2) it lacks effective modeling of dynamic human interventions and environmental changes that are pervasive in real laboratory settings; and (3) it often fails to capture the full spectrum of physical constraints and noise present in experimental procedures. Consequently, there exists a substantial gap between current simulation benchmarks and the complexities agents face in real-world laboratory conditions.

To address these fundamental limitations, we propose \textbf{LabBench}, a data-driven Real-to-Sim task compilation framework and comprehensive scientific benchmark for robotic manipulation in laboratory environments. Unlike traditional approaches that require manual task engineering, LabBench automatically translates real-world experimental protocols into executable simulation code through a sophisticated neuro-symbolic pipeline. Our key insight is that by combining the semantic understanding capabilities of large language models (LLMs) with deterministic code synthesis and physics-based verification, we can create a scalable system that captures both the complexity and physical realism of laboratory work.

\paragraph{Neuro-Symbolic AST Parsing}
At the core of LabBench is a novel parser that converts raw experimental instructions into entity-bound neuro-symbolic Abstract Syntax Trees (ASTs). This approach strictly decouples semantic understanding from action execution, allowing the framework to ground natural language instructions to physical entities while maintaining clear separation between high-level reasoning and low-level control. The AST representation serves as an intermediate formalism that enables systematic translation of protocols into simulation code.

\paragraph{Parallel Dual-Planner Architecture}
LabBench introduces a parallel Dual-Planner compilation strategy that addresses the long-horizon reasoning challenge. While a state-based Chain-of-Thought (CoT) planner orchestrates continuous actions by tracking pre- and post-conditions for each step, a condition planner concurrently generates low-level physical verification criteria. This fan-in architecture enables efficient planning while ensuring that each action is associated with concrete, physically-verifiable success conditions---a critical feature for rigorous evaluation.

\paragraph{Dynamic Human Intervention Modeling}
A key innovation of LabBench is its explicit modeling of dynamic human interventions, which are ubiquitous in real laboratory settings but absent from most simulation benchmarks. Our framework approximates human-robot interaction by injecting programmatic environmental alterations---such as instrument state toggles, reagent additions, and equipment reconfigurations---directly into the experimental equipment. This capability allows LabBench to evaluate agent performance under realistic conditions where external factors can modify task dynamics mid-execution.

\paragraph{Comprehensive Benchmark}
Leveraging this automated pipeline, we have distilled protocols from frontier scientific literature to construct a benchmark containing over 100 core test tasks, including 20+ dynamic interference scenarios. These tasks cover more than 20 typical robotic manipulations and involve over 100 experimental instruments drawn from chemistry, biology, and materials science. Backed by the MuJoCo physics engine \cite{todorov2012mujoco}, our dataset generates a massive number of evaluation episodes featuring topological scene changes and realistic rigid-body physical noise, enabling thorough assessment of agent generalization capabilities.

\paragraph{Rigorous Evaluation Methodology}
LabBench employs a multi-dimensional evaluation framework that goes beyond traditional binary success metrics. Our step-by-step physical state verification exposes the overestimation inherent in coarse-grained evaluation approaches. Preliminary evaluations on mainstream policy models (ACT \cite{lee2021learning}, Diffusion Policy \cite{chi2023diffusion}, $\pi_0$ \cite{team2024open}) demonstrate the significant challenge posed by LabBench, with state-of-the-art models showing precipitous drops in success rates when rigorous physical and state validation is applied. This highlights the severe compounding error bottleneck that current models face in long-horizon manipulation tasks.

\paragraph{Contributions}
Our main contributions are:
\begin{itemize}
    \item We propose LabBench, a novel data-driven Real-to-Sim framework that automatically compiles real-world experimental protocols into physics-based simulation tasks, dramatically reducing the manual effort required for benchmark creation.
    \item We introduce a neuro-symbolic AST parsing approach combined with a parallel Dual-Planner architecture, enabling systematic translation of natural language instructions into executable code with physically-verifiable success conditions.
    \item We present dynamic human intervention modeling through programmatic environmental alterations, bringing simulation benchmarks closer to real-world laboratory complexity.
    \item We construct a comprehensive benchmark with 100+ tasks covering diverse scientific manipulations, with multi-dimensional evaluation revealing significant limitations in current state-of-the-art models.
    \item We open-source the complete pipeline code, benchmark dataset, and expert demonstration trajectories to enable community-wide advancement in scientific embodied AI.
\end{itemize}

\section{The LabBench Framework}
\label{sec:framework}

This section presents the technical architecture of LabBench, a data-driven Real-to-Sim task compilation framework. We describe the overall pipeline design and detail each major component, from instruction parsing to physics-based simulation execution.

\subsection{Overview}

LabBench employs a directed acyclic graph (DAG) pipeline architecture consisting of nine specialized nodes, as illustrated in Figure~\ref{fig:framework_overview}. The pipeline follows a strict data flow from natural language instructions to executable simulation tasks:

\begin{enumerate}
    \item \textbf{Analyzer}: Parses raw instructions into entity-bound neuro-symbolic ASTs
    \item \textbf{Normalizer}: Cleans data and assigns global unique identifiers (UIDs) to entities
    \item \textbf{Asset Manager}: Retrieves 3D models and binds them to physical instances
    \item \textbf{Skill Planner}: Orchestrates long-horizon action sequences via state-based Chain-of-Thought reasoning
    \item \textbf{Condition Planner}: Generates per-step physical verification criteria in parallel
    \item \textbf{Code Generator}: Synthesizes deterministic Python task files from templates
    \item \textbf{Registration}: Dynamically registers generated tasks into the VLABench framework
    \item \textbf{Simulation}: Executes tasks in MuJoCo physics engine with real-time condition checking
    \item \textbf{Reviewer}: Validates simulation outcomes via vision-based multimodal assessment
\end{enumerate}

This architecture embodies the principle of \textit{neuro-symbolic separation}: neural components (Analyzer, Skill Planner, Condition Planner) handle semantic understanding and reasoning, while symbolic components (Normalizer, Asset Manager, Code Generator, Simulation) ensure deterministic, physically-accurate execution.

\subsection{Neuro-Symbolic AST Parser}

The Analyzer node serves as the natural language understanding frontend of LabBench. Given a raw experimental instruction such as ``Pick up the beaker from the water bath and pour its contents into the test tube rack,'' the Analyzer produces a structured neuro-symbolic AST that captures both semantic intent and entity relationships.

\textbf{Entity Extraction.} The Analyzer employs a large language model to identify physical objects and their semantic attributes from the instruction. Each entity is assigned a placeholder identifier (e.g., \texttt{<beaker\_0>}, \texttt{<test\_tube\_0>}) and associated with attribute tags including object type, spatial relations, and functional properties. The extraction follows the principle of \textit{explicit intent only}: the analyzer does not infer implicit actions not stated in the instruction, ensuring faithful representation of the user's intent.

\textbf{Step Grounding.} The instruction is decomposed into a sequence of grounded steps, where each step references concrete entity identifiers. This creates a preliminary action graph where nodes represent entities and edges represent relationships (spatial, functional, or causal). For example, the pouring instruction yields steps such as: (1) approach \texttt{<beaker\_0>}, (2) grasp \texttt{<beaker\_0>}, (3) lift \texttt{<beaker\_0>} to height $h$, (4) tilt and pour into \texttt{<test\_tube\_0>}.

\textbf{Abstract Syntax Tree.} The grounded steps are organized into an AST structure that maintains the hierarchical and sequential dependencies between actions. Each AST node contains: (i) the semantic operation type, (ii) references to input/output entities, (iii) pre-conditions, and (iv) post-conditions. This formal representation serves as the canonical intermediate format consumed by subsequent pipeline stages.

\subsection{Automatic Scene Construction}

The Normalizer and Asset Manager nodes collaborate to transform the abstract AST into a concrete physical scene instantiation.

\textbf{Normalization and UID Assignment.} The Normalizer receives the AST with placeholder entity identifiers and performs several essential transformations: (1) \textit{Data cleaning}: standardizes entity names, resolves synonyms, and filters non-physical entities (powders, liquids) that cannot be directly manipulated; (2) \textit{Global UID assignment}: replaces placeholder identifiers with globally unique IDs that persist across pipeline stages; (3) \textit{Asset routing}: determines whether each entity should be retrieved from local cache, constant definitions, or the Objaverse asset library \cite{deitke2023objaverse}; and (4) \textit{Parameter translation}: converts semantic attributes into physical initialization parameters (positions, orientations, masses).

\textbf{Asset Retrieval and Binding.} The Asset Manager handles the physical instantiation of entities by: (1) querying the multi-tier asset cache (local files $\rightarrow$ constant definitions $\rightarrow$ Objaverse download); (2) performing dynamic class inference for entities with ambiguous types (e.g., distinguishing chemistry containers from common graspable objects); (3) injecting surgical XML modifications into MuJoCo model files to support specialized physics (e.g., adding solution sites to containers); and (4) performing fail-fast validation to ensure all required assets are available before proceeding to planning.

This separation of concerns---Normalizer handles semantic-to-physical translation while Asset Manager handles physical instantiation---enables clean modularity and facilitates error handling. The design principle of \textit{issuing commands, not performing manual labor} ensures that the Asset Manager never engages in LLM-based reasoning, but rather executes strongly-typed parameter-driven operations.

\subsection{Dual-Planner Compilation}

The core compilation intelligence resides in the parallel Dual-Planner, which consists of two cooperating planners that receive identical normalized context and asset status information.

\subsubsection{Skill Planner: State-based Chain-of-Thought Reasoning}

The Skill Planner addresses the challenge of long-horizon manipulation by employing a state-based Chain-of-Thought (CoT) planning approach. Unlike traditional planning systems that rely on hardcoded rules or iterative refinement loops, our planner operates as a \textit{stateful one-shot planner}:

\textbf{Pre/Post State Assertions.} For each action in the planned sequence, the Skill Planner explicitly specifies both the pre-state (conditions that must hold before execution) and post-state (conditions that result from execution). This enables precise tracking of entity states throughout the task. For example, before grasping a beaker: pre-state asserts that the robot end-effector is empty and the beaker is at its initial position; post-state asserts that the beaker is now constrained to the gripper and its position has changed.

\textbf{Skill Library Integration.} The planner draws from a library of primitive skills including: \texttt{pick}, \texttt{place}, \texttt{lift}, \texttt{drop}, \texttt{pour\_to\_entity}, \texttt{stir\_entity\_with\_tool}, \texttt{shake}, \texttt{insert\_to\_entity}, \texttt{unscrew\_cap}, \texttt{open\_drawer}, \texttt{wait\_for}. Each skill is parameterized with entity references and physical targets (heights, angles, durations).

\textbf{Zero Hardcoded Rules.} The planning process is entirely LLM-driven, with no hardcoded domain-specific rules. The planner's reasoning is guided solely by the state assertions and the skill library specifications, enabling generalization to novel task combinations.

\subsubsection{Condition Planner: Physical Verification Criteria}

In parallel with skill planning, the Condition Planner generates per-step physical verification criteria that enable rigorous task evaluation. This addresses a critical limitation of traditional benchmarks that rely on coarse-grained binary success metrics.

\textbf{Per-Step Condition Generation.} For each action step, the Condition Planner generates specific, physically-verifiable conditions. Rather than evaluating only final task completion, conditions are attached to intermediate states. For example, for a pouring task: (1) grasp condition verifies contact between gripper and beaker; (2) lift condition verifies beaker height exceeds threshold; (3) pour condition verifies liquid mass transfer between containers; (4) release condition verifies beaker placement at target location.

\textbf{Condition Types.} The condition library includes: \texttt{is\_grasped} (entity constrained to gripper), \texttt{lift} (entity at or above specified height), \texttt{on} (entity in contact with specified surface), \texttt{contain} (entity volume occupied by target substance), \texttt{pour\_into} (mass transfer between containers), \texttt{stir} (rotational motion applied), \texttt{cap\_open} (container lid state), \texttt{wait\_for} (state change after duration).

\textbf{Fan-in Architecture.} The parallel execution of Skill Planner and Condition Planner constitutes a \textit{fan-in} architecture: both planners receive identical inputs and operate independently, with their outputs merged at the Code Generator. This design maximizes efficiency by enabling concurrent processing while maintaining coherence through shared context.

\subsection{Dynamic Human Intervention Modeling}

A distinguishing feature of LabBench is its explicit modeling of dynamic human interventions, which are ubiquitous in real laboratory settings but absent from most simulation benchmarks. We introduce a mechanism for approximating human-robot interaction through \textit{programmatic environmental alterations}.

\textbf{Intervention Types.} LabBench supports several categories of interventions: (1) \textit{Instrument state toggles}: opening/closing valves, switching heaters on/off, activating stirrers; (2) \textit{Reagent additions}: introducing additional substances mid-task that may affect reaction dynamics; (3) \textit{Equipment reconfiguration}: repositioning support structures, changing container arrangements; and (4) \textit{External perturbations}: applying forces or disturbances to objects during execution.

\textbf{Implementation.} Interventions are specified as state modifications that alter the environmental conditions during task execution. They are injected programmatically through the Simulation node, which modifies entity states, adds or removes substances, or applies forces according to predefined intervention scripts. Each intervention is associated with timing information (when to trigger) and effect parameters (magnitude, duration).

\textbf{Evaluation Impact.} By introducing interventions, LabBench creates dynamic interference scenarios that evaluate an agent's ability to: (i) detect and respond to unexpected changes, (ii) adapt plans in response to altered conditions, and (iii) maintain task coherence despite external perturbations. These scenarios reveal robustness issues that would be hidden in static evaluation settings.

\subsection{Code Generation and Simulation}

The final stages of the pipeline transform the planned skill sequences and verification conditions into executable simulation code.

\textbf{Deterministic Code Synthesis.} The Code Generator operates as a deterministic template filler: given the normalized entity list, skill sequence, and condition specifications, it produces a Python task file with identical structure regardless of the specific task content. This deterministic property ensures \textit{reproducibility}: the same inputs always produce bit-identical outputs, facilitating debugging and result replication.

The generated code follows the VLABench task structure, defining: (i) a \texttt{ConfigManager} class that specifies entity configurations, initial conditions, and instruction text; (ii) a \texttt{Task} class that implements the \texttt{get\_expert\_skill\_sequence()} method returning the planned skill chain; and (iii) condition bindings that connect verification criteria to physics engine observations.

\textbf{Dynamic Registration.} The Registration node makes newly generated tasks discoverable by the VLABench framework without requiring process restart. It performs module cleanup, updates the dual name-to-config registry, and persists task configurations to enable retrieval by the evaluation infrastructure.

\textbf{Physics Simulation and Verification.} The Simulation node loads the registered task, initializes the MuJoCo physics environment with the configured scene, and executes the expert skill sequence. During execution, per-step conditions are evaluated against physics engine state observations. The simulation supports: (i) early termination upon condition failure, (ii) timeout protection for unbounded execution, (iii) HDF5-format data logging for observation/action trajectories, and (iv) video recording for visual inspection.

\textbf{Vision-based Review.} The Reviewer node provides an additional validation layer by employing a vision-language model to assess simulation outcomes. It extracts frames from simulation videos and prompts the VLM to verify whether conditions were satisfied according to visual evidence. This addresses cases where physics engine state may not fully capture task success (e.g., liquid spillage, object deformation).

\section{The LabBench Benchmark}
\label{sec:benchmark}

This section presents the LabBench benchmark, a comprehensive evaluation framework for scientific embodied agents. We describe the task design philosophy, evaluation dimensions, data generation methodology, and infrastructure that together enable rigorous and scalable assessment of robotic manipulation capabilities.

\subsection{Task Design and Coverage}

The LabBench benchmark is constructed through automated compilation of real-world experimental protocols from frontier scientific literature. Our task design follows three core principles: \textit{physical realism} (tasks reflect actual laboratory procedures), \textit{manipulation diversity} (coverage of varied instrument types and operation sequences), and \textit{evaluation rigor} (granular condition-based assessment).

\textbf{Core Task Statistics.} The benchmark contains 100+ core test tasks, encompassing 20+ typical robotic manipulation categories and 100+ experimental instruments. Task coverage spans multiple scientific domains including chemistry (beakers, test tubes, flasks, funnels, thermometers), biology (petri dishes, pipettes, microscope slides), and materials science (weighing boats, crucibles, heating plates). \textbf{Task Taxonomy.} LabBench tasks are organized hierarchically into two tiers:

\textit{Primitive tasks} focus on individual manipulation operations: \texttt{pick\_beaker}, \texttt{lift\_tube}, \texttt{pour\_beaker}, \texttt{stir\_flask}, \texttt{insert\_rod}, \texttt{open\_drawer}, \texttt{weight\_cylinder}. These tasks evaluate fundamental sensorimotor capabilities and serve as building blocks for complex procedures.

\textit{Composite tasks} chain multiple primitive operations into coherent experimental workflows: \texttt{pick\_tube\_pour\_object} (pick, transport, pour), \texttt{put\_small\_beaker\_wait\_for\_object\_lift} (pick, wait, respond). These tasks assess long-horizon reasoning, state tracking, and sequential planning.

\textbf{Dynamic Interference Scenarios.} A distinguishing feature of LabBench is its inclusion of 20+ dynamic interference scenarios that model real-world human-robot collaboration. These scenarios introduce programmatic environmental alterations during task execution, such as: a colleague adjusting a valve while the robot transfers reagents, temperature changes affecting reaction kinetics, or support structures being repositioned mid-procedure. These scenarios evaluate agent robustness and adaptive planning capabilities beyond static evaluation settings.

\subsection{Evaluation Dimensions}

LabBench employs a multi-dimensional evaluation framework that decomposes agent capabilities into six complementary aspects. This design enables fine-grained diagnostic assessment beyond monolithic success metrics.

\textbf{Manipulation \& Tool (M\&T).} This dimension evaluates fundamental manipulation capabilities including grasping, lifting, placing, pouring, and tool use. Tasks assess gripper-object interaction, object-object relations (e.g., placing a beaker onto a support), and coordinated dual-hand operations. Example tasks: pick funnel from support, place large beaker on surface, insert stirring rod into flask.

\textbf{Spatial Reasoning.} This dimension tests the agent's understanding of spatial relationships and geometry. Tasks involve arranging objects according to specifications, navigating around obstacles, and positioning objects with precise orientation requirements. Example tasks: align test tube with rack hole, position weighing boat centered on scale, orient flask cap for screwing.

\textbf{CommonSense Reasoning.} This dimension evaluates intuitive physics understanding that humans apply automatically in laboratory settings. Tasks involve predicting object stability (will this stack topple?), estimating quantities (is this container full?), and reasoning about causal relationships (what happens if I tilt before grasping?). Example tasks: avoid placing heavy object on fragile surface, estimate when liquid reaches target volume.

\textbf{Semantic Understanding.} This dimension assesses language grounding and instruction following in ambiguous or underspecified contexts. Tasks involve resolving referring expressions (``the beaker on the left''), handling negation and constraint modifiers (``do not touch the thermometer''), and integrating textual specifications with visual observations. Example tasks: pick the beaker indicated in the instruction, place the marked tube in the highlighted position.

\textbf{Physical Law Reasoning.} This dimension tests understanding of physical principles underlying laboratory procedures. Tasks involve reasoning about heat transfer, fluid dynamics, material properties, and chemical interactions. Example tasks: predict temperature equilibrium time, estimate pour rate based on viscosity, select appropriate container for heated substances.

\textbf{Complex Multi-Step Reasoning.} This dimension evaluates long-horizon planning and execution in tasks requiring 5+ sequential operations with interleaved conditions. Tasks simulate complete experimental protocols where each step's preconditions depend on prior actions. Example tasks: complete a titration procedure (prepare, transfer, titrate, measure, clean), conduct a filtration workflow (assemble, pour, wait, collect, disassemble).

The six dimensions are designed to be complementary and non-redundant: an agent may excel at Manipulation \& Tool while struggling with Complex reasoning, revealing specific capability gaps that inform development priorities.

\subsection{Data Generation and Asset Pipeline}

The benchmark's scale and diversity are enabled by LabBench's automated data generation pipeline, which transforms source protocols into physics-based evaluation episodes.

\textbf{Expert Trajectory Collection.} For each task, expert demonstration trajectories are collected by executing the planned skill sequences in simulation. These trajectories record: (i) full observation sequences (RGB images from multiple viewpoints, depth maps, proprioceptive state), (ii) action sequences (end-effector waypoints, gripper commands), and (iii) condition evaluation logs at each timestep. Trajectories are collected with randomized initial object poses to ensure generalization beyond fixed configurations.

\textbf{Episode Generation with Physical Variations.} From each task, we generate multiple evaluation episodes by applying domain randomization across: object initial positions (uniform sampling within workspace bounds), object initial orientations (full rotation range), camera viewpoints (varied elevation and azimuth), lighting conditions (intensity and color temperature), and object material textures (randomized surface properties). This yields episodes featuring realistic topological scene changes and rigid-body physical noise.

\textbf{VLM Evaluation Dataset.} For vision-language model evaluation, we construct a structured dataset of 4,100 episodes with standardized input/output formats. Each episode provides: (i) rendered scene images with annotated instructions, (ii) ground-truth skill sequences and operation timings, and (iii) environment configuration files enabling deterministic replay. The dataset is partitioned by evaluation dimension (M\&T, Spatial, CommonSense, Semantic, PhysicalLaw, Complex) with task-stratified splits.

\textbf{Asset Diversity.} The benchmark's 100+ instruments are sourced from multiple asset libraries with quality curation. Primary sources include: Objaverse \cite{deitke2023objaverse} (large-scale 3D asset repository), local laboratory equipment models (custom-built for scientific accuracy), and procedural geometry generation for specialized components. Each asset undergoes physics validation to ensure realistic contact, friction, and constraint behaviors in simulation.

\subsection{Evaluation Infrastructure}

LabBench provides a comprehensive evaluation infrastructure supporting both policy model (VLA) and vision-language model (VLM) assessment.

\textbf{Evaluation Tracks.} The benchmark defines six standardized evaluation tracks corresponding to different generalization scenarios:

\begin{enumerate}
    \item \textbf{Track 1: In-Distribution}: Tasks trained on, evaluated on matching configurations
    \item \textbf{Track 2: Cross-Category}: Trained on one object category, tested on another (e.g., trained on glass beakers, tested on plastic beakers)
    \item \textbf{Track 3: Common-Sense}: Evaluates common sense reasoning generalization
    \item \textbf{Track 4: Semantic Instruction}: Tests semantic understanding with novel phrasings
    \item \textbf{Track 5: Cross-Task}: Trained on task subset, tested on unseen task combinations
    \item \textbf{Track 6: Unseen Texture}: Evaluates visual robustness to novel materials
\end{enumerate}

\textbf{Evaluation Metrics.} LabBench employs multi-level metrics that capture both coarse and fine-grained performance:

\begin{itemize}
    \item \textbf{Success Rate}: Binary task completion indicator (1 if all conditions satisfied, 0 otherwise)
    \item \textbf{Intention Score}: Measures whether agent actions align with task goal, ranging from 0 (no progress) to 1 (full completion)
    \item \textbf{Progress Score}: Soft metric capturing partial condition satisfaction, enabling analysis of failure modes
    \item \textbf{Condition Results}: Per-condition pass/fail breakdown revealing specific failure points
\end{itemize}

Critically, LabBench's step-by-step condition verification provides diagnostic information unavailable in binary-only evaluation. For instance, an agent may achieve 100\% success rate under binary metrics but fail physical verification at intermediate steps---revealing compensating errors that mask underlying failures.

\textbf{Evaluation Protocol.} The standard evaluation protocol proceeds as follows: (i) load task configuration and initialize MuJoCo environment with randomized parameters; (ii) execute agent policy (or prompt VLM) to generate action predictions; (iii) step simulation forward while evaluating conditions at each timestep; (iv) compute metrics upon episode termination (success, timeout, or max steps); (v) aggregate results across episodes using task-weighted averaging. All evaluation runs produce structured logs (JSON) and visualization videos (MP4) for post-hoc analysis.

Note that the \textbackslash thanks command is fragile. You will need to use \textbackslash protect.

Please do not include \textbackslash pubnote commands in your document.

\subsection{Abstract}
Follow the example commands in this document for creation of your abstract. The command \textbackslash begin\{abstract\} will automatically indent the text block. Please do not indent it further. {Do not include references in your abstract!}

\subsection{Page Numbers}

Do not print any page numbers on your paper. The use of \textbackslash pagestyle is forbidden.

\subsection{Text}
The main body of the paper must be formatted in black, ten-point Times Roman with twelve-point leading (line spacing). You may not reduce font size or the linespacing. Commands that alter font size or line spacing (including, but not limited to baselinestretch, baselineshift, linespread, and others) are expressly forbidden. In addition, you may not use color in the text.

\subsection{Citations}
Citations within the text should include the author's last name and year, for example (Newell 1980). Append lower-case letters to the year in cases of ambiguity. Multiple authors should be treated as follows: (Feigenbaum and Engelmore 1988) or (Ford, Hayes, and Glymour 1992). In the case of four or more authors, list only the first author, followed by et al. (Ford et al. 1997).

\subsection{Extracts}
Long quotations and extracts should be indented ten points from the left and right margins.

\begin{quote}
This is an example of an extract or quotation. Note the indent on both sides. Quotation marks are not necessary if you offset the text in a block like this, and properly identify and cite the quotation in the text.

\end{quote}

\subsection{Footnotes}
Use footnotes judiciously, taking into account that they interrupt the reading of the text. When required, they should be consecutively numbered throughout with superscript Arabic numbers. Footnotes should appear at the bottom of the page, separated from the text by a blank line space and a thin, half-point rule.

\subsection{Headings and Sections}
When necessary, headings should be used to separate major sections of your paper. Remember, you are writing a short paper, not a lengthy book! An overabundance of headings will tend to make your paper look more like an outline than a paper. The aaai2026.sty package will create headings for you. Do not alter their size nor their spacing above or below.

\subsubsection{Section Numbers.}
The use of section numbers in AAAI Press papers is optional. To use section numbers in \LaTeX{}, uncomment the setcounter line in your document preamble and change the 0 to a 1. Section numbers should not be used in short poster papers and/or extended abstracts.

\subsubsection{Section Headings.}
Sections should be arranged and headed as follows:
\begin{enumerate}
\item Main content sections
\item Appendices (optional)
\item Ethical Statement (optional, unnumbered)
\item Acknowledgements (optional, unnumbered)
\item References (unnumbered)
\end{enumerate}

\subsubsection{Appendices.}
Any appendices must appear after the main content. If your main sections are numbered, appendix sections must use letters instead of arabic numerals. In \LaTeX{} you can use the \texttt{\textbackslash appendix} command to achieve this effect and then use \texttt{\textbackslash section\{Heading\}} normally for your appendix sections.

\subsubsection{Ethical Statement.}
You can write a statement about the potential ethical impact of your work, including its broad societal implications, both positive and negative. If included, such statement must be written in an unnumbered section titled \emph{Ethical Statement}.

\subsubsection{Acknowledgments.}
The acknowledgments section, if included, appears right before the references and is headed ``Acknowledgments". It must not be numbered even if other sections are (use \texttt{\textbackslash section*\{Acknowledgements\}} in \LaTeX{}). This section includes acknowledgments of help from associates and colleagues, credits to sponsoring agencies, financial support, and permission to publish. Please acknowledge other contributors, grant support, and so forth, in this section. Do not put acknowledgments in a footnote on the first page. If your grant agency requires acknowledgment of the grant on page 1, limit the footnote to the required statement, and put the remaining acknowledgments at the back. Please try to limit acknowledgments to no more than three sentences.

\subsubsection{References.}
The references section should be labeled ``References" and must appear at the very end of the paper (don't end the paper with references, and then put a figure by itself on the last page). A sample list of references is given later on in these instructions. Please use a consistent format for references. Poorly prepared or sloppy references reflect badly on the quality of your paper and your research. Please prepare complete and accurate citations.

Your paper must compile in PDF\LaTeX{}. Consequently, all your figures must be .jpg, .png, or .pdf. You may not use the .gif (the resolution is too low), .ps, or .eps file format for your figures.

Figures, drawings, tables, and photographs should be placed throughout the paper on the page (or the subsequent page) where they are first discussed. Do not group them together at the end of the paper. If placed at the top of the paper, illustrations may run across both columns. Figures must not invade the top, bottom, or side margin areas. Figures must be inserted using the \textbackslash usepackage\{graphicx\}. Number figures sequentially, for example, figure 1, and so on. Do not use minipage to group figures.

If you normally create your figures using pgfplots, please create the figures first, and then import them as pdfs with proper bounding boxes, as the bounding and trim boxes created by pfgplots are fragile and not valid.

When you include your figures, you must crop them \textbf{outside} of \LaTeX{}. The command \textbackslash includegraphics*[clip=true, viewport 0 0 10 10]{...} might result in a PDF that looks great, but the image is \textbf{not really cropped.} The full image can reappear (and obscure whatever it is overlapping) when page numbers are applied or color space is standardized. Figures \ref{fig1}, and \ref{fig2} display some unwanted results that often occur.

If your paper includes illustrations that are not compatible with PDF\TeX{} (such as .eps or .ps documents), you will need to convert them. The epstopdf package will usually work for eps files. You will need to convert your ps files to PDF in either case.

\subsubsection {Figure Captions.}The illustration number and caption must appear \textit{under} the illustration. Labels and other text with the actual illustration must be at least nine-point type. However, the font and size of figure captions must be 10 point roman. Do not make them smaller, bold, or italic. (Individual words may be italicized if the context requires differentiation.)

\subsection{Tables}

\subsection{Tables}

Tables should be presented in 10 point roman type. If necessary, they may be altered to 9 point type. You must not use \texttt{\textbackslash resizebox} or other commands that resize the entire table to make it smaller, because you can't control the final font size this way.
If your table is too large you can use \texttt{\textbackslash setlength\{\textbackslash tabcolsep\}\{1mm\}} to compress the columns a bit or you can adapt the content (e.g.: reduce the decimal precision when presenting numbers, use shortened column titles, make some column duble-line to get it narrower).

Tables that do not fit in a single column must be placed across double columns. If your table won't fit within the margins even when spanning both columns and using the above techniques, you must split it in two separate tables.

\subsubsection {Table Captions.} The number and caption for your table must appear \textit{under} (not above) the table.  Additionally, the font and size of table captions must be 10 point roman and must be placed beneath the figure. Do not make them smaller, bold, or italic. (Individual words may be italicized if the context requires differentiation.)



\subsubsection{Low-Resolution Bitmaps.}
You may not use low-resolution (such as 72 dpi) screen-dumps and GIF files---these files contain so few pixels that they are always blurry, and illegible when printed. If they are color, they will become an indecipherable mess when converted to black and white. This is always the case with gif files, which should never be used. The resolution of screen dumps can be increased by reducing the print size of the original file while retaining the same number of pixels. You can also enlarge files by manipulating them in software such as PhotoShop. Your figures should be 300 dpi when incorporated into your document.

\subsubsection{\LaTeX{} Overflow.}
\LaTeX{} users please beware: \LaTeX{} will sometimes put portions of the figure or table or an equation in the margin. If this happens, you need to make the figure or table span both columns. If absolutely necessary, you may reduce the figure, or reformat the equation, or reconfigure the table.{ \bf Check your log file!} You must fix any overflow into the margin (that means no overfull boxes in \LaTeX{}). \textbf{Nothing is permitted to intrude into the margin or gutter.}


\subsubsection{Using Color.}
Use of color is restricted to figures only. It must be WACG 2.0 compliant. (That is, the contrast ratio must be greater than 4.5:1 no matter the font size.) It must be CMYK, NOT RGB. It may never be used for any portion of the text of your paper. The archival version of your paper will be printed in black and white and grayscale. The web version must be readable by persons with disabilities. Consequently, because conversion to grayscale can cause undesirable effects (red changes to black, yellow can disappear, and so forth), we strongly suggest you avoid placing color figures in your document. If you do include color figures, you must (1) use the CMYK (not RGB) colorspace and (2) be mindful of readers who may happen to have trouble distinguishing colors. Your paper must be decipherable without using color for distinction.

\subsubsection{Drawings.}
We suggest you use computer drawing software (such as Adobe Illustrator or, (if unavoidable), the drawing tools in Microsoft Word) to create your illustrations. Do not use Microsoft Publisher. These illustrations will look best if all line widths are uniform (half- to two-point in size), and you do not create labels over shaded areas. Shading should be 133 lines per inch if possible. Use Times Roman or Helvetica for all figure call-outs. \textbf{Do not use hairline width lines} --- be sure that the stroke width of all lines is at least .5 pt. Zero point lines will print on a laser printer, but will completely disappear on the high-resolution devices used by our printers.

\subsubsection{Photographs and Images.}
Photographs and other images should be in grayscale (color photographs will not reproduce well; for example, red tones will reproduce as black, yellow may turn to white, and so forth) and set to a minimum of 300 dpi. Do not prescreen images.

\subsubsection{Resizing Graphics.}
Resize your graphics \textbf{before} you include them with LaTeX. You may \textbf{not} use trim or clip options as part of your \textbackslash includegraphics command. Resize the media box of your PDF using a graphics program instead.

\subsubsection{Fonts in Your Illustrations.}
You must embed all fonts in your graphics before including them in your LaTeX document.

\subsubsection{Algorithms.}
Algorithms and/or programs are a special kind of figures. Like all illustrations, they should appear floated to the top (preferably) or bottom of the page. However, their caption should appear in the header, left-justified and enclosed between horizontal lines, as shown in Algorithm~\ref{alg:algorithm}. The algorithm body should be terminated with another horizontal line. It is up to the authors to decide whether to show line numbers or not, how to format comments, etc.

In \LaTeX{} algorithms may be typeset using the {\tt algorithm} and {\tt algorithmic} packages, but you can also use one of the many other packages for the task.

\begin{algorithm}[tb]
\caption{Example algorithm}
\label{alg:algorithm}
\textbf{Input}: Your algorithm's input\\
\textbf{Parameter}: Optional list of parameters\\
\textbf{Output}: Your algorithm's output
\begin{algorithmic}[1] %[1] enables line numbers
\STATE Let $t=0$.
\WHILE{condition}
\STATE Do some action.
\IF {conditional}
\STATE Perform task A.
\ELSE
\STATE Perform task B.
\ENDIF
\ENDWHILE
\STATE \textbf{return} solution
\end{algorithmic}
\end{algorithm}

\subsubsection{Listings.}
Listings are much like algorithms and programs. They should also appear floated to the top (preferably) or bottom of the page. Listing captions should appear in the header, left-justified and enclosed between horizontal lines as shown in Listing~\ref{lst:listing}. Terminate the body with another horizontal line and avoid any background color. Line numbers, if included, must appear within the text column.

\begin{listing}[tb]%
\caption{Example listing {\tt quicksort.hs}}%
\label{lst:listing}%
\begin{lstlisting}[language=Haskell]
quicksort :: Ord a => [a] -> [a]
quicksort []     = []
quicksort (p:xs) = (quicksort lesser) ++ [p] ++ (quicksort greater)
	where
		lesser  = filter (< p) xs
		greater = filter (>= p) xs
\end{lstlisting}
\end{listing}

\subsection{References}
The AAAI style includes a set of definitions for use in formatting references with BibTeX. These definitions make the bibliography style fairly close to the ones  specified in the Reference Examples appendix below. To use these definitions, you also need the BibTeX style file ``aaai2026.bst," available in the AAAI Author Kit on the AAAI web site. Then, at the end of your paper but before \textbackslash end{document}, you need to put the following lines:

\begin{quote}
\begin{small}
\textbackslash bibliography\{bibfile1,bibfile2,...\}
\end{small}
\end{quote}

Please note that the aaai2026.sty class already sets the bibliographystyle for you, so you do not have to place any \textbackslash bibliographystyle command in the document yourselves. The aaai2026.sty file is incompatible with the hyperref and navigator packages. If you use either, your references will be garbled and your paper will be returned to you.

References may be the same size as surrounding text.
However, in this section (only), you may reduce the size to {\em \textbackslash small} (9pt) if your paper exceeds the allowable number of pages. Making it any smaller than 9 point with 10 point linespacing, however, is not allowed.

The list of files in the \textbackslash bibliography command should be the names of your BibTeX source files (that is, the .bib files referenced in your paper).

The following commands are available for your use in citing references:
\begin{quote}
{\em \textbackslash cite:} Cites the given reference(s) with a full citation. This appears as ``(Author Year)'' for one reference, or ``(Author Year; Author Year)'' for multiple references.\smallskip\\
{\em \textbackslash shortcite:} Cites the given reference(s) with just the year. This appears as ``(Year)'' for one reference, or ``(Year; Year)'' for multiple references.\smallskip\\
{\em \textbackslash citeauthor:} Cites the given reference(s) with just the author name(s) and no parentheses.\smallskip\\
{\em \textbackslash citeyear:} Cites the given reference(s) with just the date(s) and no parentheses.
\end{quote}
You may also use any of the \emph{natbib} citation commands.

\section{Reference Examples}
\label{sec:reference_examples}

\nobibliography*
Formatted bibliographies should look like the following examples. You should use BibTeX to generate the references. Missing fields are unacceptable when compiling references, and usually indicate that you are using the wrong type of entry (BibTeX class).

\paragraph{Book with multiple authors~\nocite{em:86}} Use the \texttt{@book} class.\\[.2em]
\bibentry{em:86}.

\paragraph{Journal and magazine articles~\nocite{r:80, hcr:83}} Use the \texttt{@article} class.\\[.2em]
\bibentry{r:80}.\\[.2em]
\bibentry{hcr:83}.

\paragraph{Proceedings paper published by a society, press or publisher~\nocite{c:83, c:84}} Use the \texttt{@inproceedings} class. You may abbreviate the \emph{booktitle} field, but make sure that the conference edition is clear.\\[.2em]
\bibentry{c:84}.\\[.2em]
\bibentry{c:83}.

\paragraph{University technical report~\nocite{r:86}} Use the \texttt{@techreport} class.\\[.2em]
\bibentry{r:86}.

\paragraph{Dissertation or thesis~\nocite{c:79}} Use the \texttt{@phdthesis} class.\\[.2em]
\bibentry{c:79}.

\paragraph{Forthcoming publication~\nocite{c:21}} Use the \texttt{@misc} class with a \texttt{note="Forthcoming"} annotation.
\begin{quote}
\begin{footnotesize}
\begin{verbatim}
@misc(key,
  [...]
  note="Forthcoming",
)
\end{verbatim}
\end{footnotesize}
\end{quote}
\bibentry{c:21}.

\paragraph{ArXiv paper~\nocite{c:22}} Fetch the BibTeX entry from the "Export Bibtex Citation" link in the arXiv website. Notice it uses the \texttt{@misc} class instead of the \texttt{@article} one, and that it includes the \texttt{eprint} and \texttt{archivePrefix} keys.
\begin{quote}
\begin{footnotesize}
\begin{verbatim}
@misc(key,
  [...]
  eprint="xxxx.yyyy",
  archivePrefix="arXiv",
)
\end{verbatim}
\end{footnotesize}
\end{quote}
\bibentry{c:22}.

\paragraph{Website or online resource~\nocite{c:23}} Use the \texttt{@misc} class. Add the url in the \texttt{howpublished} field and the date of access in the \texttt{note} field:
\begin{quote}
\begin{footnotesize}
\begin{verbatim}
@misc(key,
  [...]
  howpublished="\url{http://...}",
  note="Accessed: YYYY-mm-dd",
)
\end{verbatim}
\end{footnotesize}
\end{quote}
\bibentry{c:23}.
